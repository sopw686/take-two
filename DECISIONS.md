# Decisions

Each entry: what was decided, what else was considered, why.

## Repository and toolchain

**Own git repo inside `vocal-coach/`.** The folder sits inside a larger personal `CODE/` checkout with one unrelated commit. Alternatives: commit into the parent repo. A nested repo keeps the project's history self-contained and lets "commit after each milestone" mean something.

**uv + Python 3.12, not 3.11 or 3.13.** `py -3.11` on this machine is a Microsoft Store stub; 3.13 lacks wheels for some audio packages. uv gives a one-command env (`uv sync`) and reproducible lock. CUDA libraries are an optional extra (`[gpu]`) so a CPU-only machine installs ~1 GB less; `run.ps1` / `run.sh` add the extra automatically when `nvidia-smi` exists.

**Vite + vanilla TypeScript, no UI framework, no runtime dependencies.** Recommended by the brief; TypeScript types mirror the analysis JSON so the report cannot silently drift from the backend. The run scripts build once into `frontend/dist`, which FastAPI serves; no separate dev server is needed to use the app.

**No `make`.** Windows has none by default. `run.ps1` is the one command on Windows, `run.sh` elsewhere.

## Speech-to-text

**faster-whisper `small.en` by default, GPU when available, CPU int8 otherwise.** `small.en` was already cached on the dev machine and is a reasonable accuracy/speed point; `base.en` is a config switch (`TAKE_TWO_STT_MODEL`). GPU loading on Windows needs both `os.add_dll_directory` and a `PATH` prepend because CTranslate2 loads cuBLAS lazily with a plain `LoadLibrary`; without the PATH fix the model loads and then the first transcription fails or hangs. This pattern came from a sibling project where it was measured (20x slower on CPU).

**Whisper's own VAD filter stays on for transcription** (`vad_filter=True`, 500 ms min silence). It prevents hallucinated text ("Thank you.") inside the long deliberate pauses this product encourages; timestamps are mapped back to the original timeline, so pauses are not lost. Pause *measurement* never uses Whisper gaps alone (below).

**Own PyAV decoder instead of `faster_whisper.audio.decode_audio`.** PyAV 15+ removed the `metadata_errors` kwarg that faster-whisper 1.2 still passes, so the bundled decoder crashes with current PyAV. A 15-line decoder using the same resampler keeps browser webm/opus, wav, m4a and mp3 working without system ffmpeg and without pinning an old PyAV.

**OpenAI Whisper API adapter only; Deepgram skipped.** The brief said not to block on cloud adapters. The OpenAI path is implemented but unverified (no key); the UI banner says when audio leaves the machine.

## Pause detection

**Silero VAD as bundled in faster-whisper (onnxruntime), RMS energy as fallback.** Alternatives: `webrtcvad` (needs a compiler or a third-party wheel), `silero-vad` package (pulls in torch, ~2 GB). faster-whisper already ships the Silero ONNX model, so this costs no dependency. Silences shorter than `min_silence_s` (0.15 s, adjustable) are ignored.

**A pause at a mark = the longest VAD silence whose midpoint lies between the start of the aligned word before the mark and the end of the aligned word after it.** This is robust to Whisper smearing word boundaries across the silence. The raw Whisper gap is stored next to it (`whisper_gap_s`) so every number can be cross-checked. If a neighbouring word was not aligned, the nearest aligned word on that side (within the take) is used; if none exists the mark is "not measurable" rather than scored.

## Alignment and rates

**`difflib.SequenceMatcher` on normalized tokens.** Needleman–Wunsch with a similarity matrix was considered; SequenceMatcher handles skipped lines, ad-libs and repeated words well enough for scripts of a few hundred words and needs no extra code. Normalization lowercases, strips punctuation and apostrophes, splits hyphens, and expands digits and `%` to words so "95%" and "ninety five percent" match. Years and misheard words were a known gap here until M12 (see "Alignment that survives real speakers").

**Words per minute uses the script's word count across the aligned span, divided by the span's duration**, not the number of matched words. A mis-transcribed word inside a line ("bleaching" heard as "leaching") would otherwise read as slower speech. A line counts as found when at least half its words align (adjustable); below that it is reported as "not found in this take".

**[KEY] status has two parts.** Rate: met if at least `key_slower_pct` slower than the speaker's own median, near if slower but not by that much, diverged if faster than the median. Pause after: met/short/missing against `key_pause_after_s`. Overall: met only if both met; diverged if the rate diverged or the pause is missing; near otherwise. The median excludes lines under 4 words (adjustable).

**Section tolerance has a 3-second floor.** A 10 % tolerance on a 20-second section is 2 s, which is below the timing noise of word timestamps.

## Values made concrete

**No score, no grades, no universal defaults.** Every threshold is in Settings and travels with the request; the analysis JSON stores the settings it was computed with. The "conference conventions" preset is a checkbox that is off by default and its numbers only appear when it is on.

**Playback serves the 16 kHz WAV, not the browser's webm.** MediaRecorder's webm lacks duration metadata, so seeking to a line's start time is unreliable; the WAV seeks exactly. The original upload is kept alongside.

**Takes are directories of files** (`takes/<id>/audio.orig.*, audio.wav, script.md, transcript.json, analysis.json`). Re-analysis reuses the stored transcript, so changing a threshold or a mark never re-runs speech-to-text.

**The "current section" shown while rehearsing is the *planned* section** at the elapsed time (cumulative budgets), labelled as such. Live speech recognition in the browser is a stretch item; a plan-based indicator is honest and works everywhere.

## Stretch features

**`TAKE_TWO_LLM=fake` is a labelled development stand-in, not a fallback.** The brief forbids substituting a heuristic for suggestions when no key is set, and the app obeys: without a key the button is disabled with a one-line reason. The fake exists only so the review UI (ghost marks, reasons, accept/reject, caps) can be exercised and demoed without spending on a model; the UI names the provider "fake (development stand-in, not a real model)".

**Live pace is opt-in and warns about where the audio goes.** The Web Speech API in Chrome sends audio to Google. That contradicts "audio stays local", so the live pace checkbox is off by default, carries the warning inline, and the whole panel is hidden where the API does not exist. The measured report never depends on it.

**Coaching gets measurements and history, never audio.** The coaching prompt receives a compacted JSON of marks and outcomes (plus the same marks' outcomes in earlier takes of the same script) and must cite a number in every suggestion; code drops suggestions without one and caps at three. If every mark was met, the model is not even called.

**Takes are grouped by a whitespace-insensitive hash of the script text.** Comparison therefore works across takes of the same script even after cosmetic edits, and stops working after a real edit, which is the right behaviour: the marks moved.

**Emphasis uses Praat (parselmouth) when installed, else librosa's pyin, else loudness only.** All three are optional so a minimal install still runs; the status is labelled experimental in the UI and the thresholds (+3 dB or +10 % pitch over the line's median) are deliberately coarse.

**Conventions preset nudges Whisper with a filler-laden prompt only when the preset is on.** Whisper suppresses "um"/"uh" by default; an `initial_prompt` containing fillers makes it transcribe them more often. Doing that always would change transcripts for users who never asked for filler counts.

## Improvise

**Improvise is a deliberate exception to "no universal defaults", handled as bands, not scores.** Without a script there are no marks to compare against, so each measure gets a reference band (pace 130–170 wpm, ≤ 2 fillers per 100 words, ≥ 5 semitones of pitch range, …) that lives in Settings next to everything else and travels with the request. Statuses read "within / close to / outside your band"; there is no overall confidence or engagement score, because a single number hides which thing to practise.

**Clarity is a proxy, not pronunciation scoring.** Real pronunciation assessment needs a phoneme-level reference model (for example a cloud pronunciation API), which would send audio off the machine. Whisper already returns a per-word confidence; words below a threshold are shown as "hard to catch", labelled as a proxy for mumbling or swallowed endings. A cloud phoneme scorer can be added later behind the same banner as cloud transcription.

**Pitch comes from Praat (parselmouth), now a runtime dependency.** Uptalk, monotone and opening energy are central to Improvise rather than an experimental extra, so `praat-parselmouth` moved from the `emphasis` extra into the main dependencies. librosa's pyin and "not measurable" remain as fallbacks. Uptalk is the last 40 % of a statement-final word's voiced frames against its first 60 %, in semitones; sentences ending in "?" are excluded. Monotone is the 10th–90th percentile pitch spread over the take.

**Hesitation vs. deliberate pauses depends on where the silence falls.** A VAD silence after a word ending in `. ? !` and under 3 s is a deliberate pause between sentences, which the engagement card counts in your favour; the same silence mid-sentence, or over 3 s between sentences, is a hesitation. This uses Whisper's punctuation, which is imperfect, but the alternative (no distinction) would penalise the pauses Take Two encourages elsewhere.

**"kind of" and "sort of" are hedges in Improvise, fillers in the conventions preset.** Counting them twice would inflate both; Improvise skips them as fillers and drops noun uses ("a kind of tree").

**Whisper is always nudged to keep fillers in Improvise.** Fillers are the point of the mode, so the filler-laden `initial_prompt` is always sent, unlike script takes where it is tied to the conventions preset.

**Drills are written by code, coaching by the model.** Up to three drills are generated from the measures furthest outside their bands, each citing the number, so the mode coaches without a key. The model's delivery coaching follows the same rules as script coaching (numbers only, cite one per suggestion, cap three) with its own prompt, which is allowed to talk about fillers and energy because the user chose this mode for that.

**Content review is opt-in per take and quote-verified.** The model reads the transcript text (never audio) and judges hook, topic, suspense and ending, each with a verbatim quote; code finds the quote and attaches timestamps or drops the item, as with `[DEFINE]`. The suggested opening line is capped at 30 words in code.

**Audio examples of engaging delivery are deferred.** Showing what a hook or a suspense pause sounds like needs recorded or generated examples; the drills describe the technique in words for now.

**Improvise takes share the take folder format** with an extra `improv.json` (topic, goal, content choice) and `mode: "improv"` in the analysis. Script-only routes (re-analysis with a script, coaching, comparison) refuse them with a 400; `/api/improv` has its own re-analysis and coaching.

## Demo safety (M8)

**A take folder is created before any processing, and a failure keeps it.** The upload, the script (or Improvise topic), the requested settings and the label go into `takes/<id>/` first, with a `take.json` recording status, the current stage and any error. Processing then resumes from the first stage whose output is missing: decoding is skipped if `audio.wav` exists, speech-to-text if `transcript.json` loads. Alternatives: keep the upload only in the browser (lost on reload, and the server already had it), or re-upload on retry (slow on a long take, and the first failure might have been the upload). This way a retry costs nothing extra, and a crash mid-transcription does not re-decode.

**"Finished" means `analysis.json` exists; `take.json`'s status only describes an unfinished take.** This keeps every older take (which has no `take.json`) working, removes a window where the two files disagree, and means a failed re-analysis of a finished take can never hide it. A take is `processing` only while this server process is working on it or has it queued; anything else left in that state (a crash, Ctrl+C, a `--reload` restart mid-take) is reported as interrupted and can be retried at once. A first version gave a take started by a different process 30 minutes' grace in case a second server shared the folder; review showed that a restarted server *is* a different process, so every interrupted take sat unretryable for half an hour. Two servers on one takes folder are not supported (the dev server uses its own folder). Status is computed when reading; listing takes never writes.

**JSON is written to a temp file and renamed into place, with retries.** With progress polling, a reader could otherwise catch half-written JSON, and on Windows OneDrive or an antivirus scan briefly holds files open, which makes the rename fail. Alternatives: a lock file (does not help a reader in another process) or a database (against the "takes are plain files" decision).

**Delete is offered only for unfinished takes in this milestone.** A failed take whose recording is gone can only be deleted; one with its recording can be retried or deleted. Deleting finished takes needs a confirmation that names the take, which comes with take management.

**The model's `[DEFINE]` judgements are cached per take, raw, and re-validated on every read.** Every Settings change re-analyzes the take, which used to cost a model call each time. The cache key is a hash of the terms, the transcript text, the provider and model, and a hash of the prompt, so any of those changing asks again. Only the model's raw answer is cached; the code that checks its quotes against the transcript runs on every read, so the cache saves the call and never skips a check. A failed call is not cached. The heuristic path needs no cache. Alternative: cache the finished rows (would bake in line numbers and skip validation).

**The example take ships a transcript produced by the real local speech-to-text, not a hand-written one.** `examples/coral/transcript.json` is one faster-whisper `small.en` run on the synthetic fixture, committed as produced, including Whisper's real mistakes ("leaching" for "bleaching", an extra "Thanks."). A hand-cleaned transcript would make the demo look better than the product is. The take is labelled "Example take (synthetic voice)" wherever it appears, and examples are left out of take comparisons, coaching history and the "your median from your latest take" estimate used by Suggest marks: a synthetic voice says nothing about the speaker.

**The run scripts rebuild the frontend when any source is newer than the build.** Comparing modification times of `frontend/src/**`, `index.html` and `package.json` against `dist/index.html` costs nothing and catches the case that bit before (a pulled or edited UI served from an old build). Alternative: always rebuild (adds a few seconds to every start).

**A fresh browser opens the newest finished take on disk.** The Report tab used to say "No take yet" whenever localStorage was empty, even with takes on disk. It now falls back to the newest finished real take, then to an example; drills are never picked.

**Recordings live wherever `TAKE_TWO_TAKES_DIR` points; the default is not moved.** On this machine the project, and so `takes/`, sits inside OneDrive, which means the sync client uploads recordings. That conflicts with "audio stays on the machine", but moving the default would hide every existing take, so the README now says so and names the variable that keeps audio local.


## Teleprompter (M9)

**The highlight follows the plan, never the voice.** Each section's budget is spread across its lines by word count, and the line whose planned window contains the elapsed time is highlighted and scrolled to about a third of the way down. The label says so: "Highlight follows your plan, not your voice." Alternatives: follow the voice with in-browser speech recognition (Chrome sends audio to Google, which breaks "audio stays local", and it is unreliable on technical vocabulary), or a fully local streaming recognizer (a large new piece of work). A plan-based highlight is honest about what it knows and matches the existing planned-section line.

**Keys re-anchor the plan instead of fighting it.** Space, ↓ and → (and PageDown, which presentation clickers send) move the highlight on; ↑, ← and PageUp move it back. The plan then continues from the chosen line at its planned pace, and the label says how far that line is from the plan ("0:12 behind your plan"), in the speaker's own budget's terms. Alternative: snap back to the plan a few seconds after a key press, which would drag the highlight away from where the speaker actually is. The clock and the planned-section line stay on real time.

**Keys work while recording unless focus is in a text field, and both halves of the key press are swallowed.** A focused button acts on Space at keyup, so stopping only keydown would let Space stop the take. The record button also gives up focus when a take starts. Enter still activates a focused Stop button.

**Scrolling by hand pauses the auto-scroll for 4 seconds, then it returns to the current line.** Wheel, touch, pointer and Home/End count as manual; programmatic scrolling cannot be told apart from user scrolling by `scroll` events, so those are not used.

**No budgets, no auto-scroll.** If any section that has lines lacks a budget, the plan is undefined, so the highlight only moves with the keys, and a note says how to turn the plan on. Partial plans were considered and rejected: the lines after an unbudgeted section would have no honest planned time.

**The client mirrors the server's parser exactly.** The teleprompter needs the same lines the report will use, so `scriptinfo.parseScript` blanks comments keeping their newlines, splits lines the way Python's `splitlines()` does, strips `[KEY]`, splits on `[DEFINE: …]` and counts words as `marks.py` does. A `[DEFINE]` term is underlined at its first occurrence in its line; if the term is not in the line, it stays a small chip where the tag was written.

## A report you can trust at a glance (M10)

**A timeline strip shows where every number comes from.** One SVG over the whole take: the voice-activity detector's silences, the span of each script line, each mark at the moment it was measured (coloured and glyphed by status), section boundaries and a playhead. Click or ←/→ seeks. It is drawn from data already in the analysis JSON; nothing new is measured for it. Coordinates are percentages of the take, so it needs no resize handling.

**Ad-libs are placed between the script words they interrupt.** The alignment already pairs script tokens with transcript words; any transcript word that matched no script word, lying between two consecutive aligned script words, becomes an ad-lib span at that spot. Between two lines it goes to the line it is closer to in time; before the first or after the last aligned word it goes to that word's line. A span that repeats the neighbouring script word is tagged as a restart. Dropped script words are flagged in the backend (only words that have something to compare; a lone dash is never "dropped"). Lines that were not found are not compared at all. The view is off by default and remembered, so the report stays calm; the line hint says "N words differ".

**Cut to fit is arithmetic at the speaker's own median.** Words = overrun × median wpm / 60, given exactly under 10 and to the nearest 5 above ("about 55 words"). It is only offered for sections that ran over by more than the tolerance, and the tooltip says it counts speaking time only (cutting lines also removes their pauses, so it errs high). The whole-talk check runs only when every section with lines has a budget and was found, from the first word to the last against the sum of the budgets, with the same tolerance rule as sections. No median, no word estimate, and the text says so.

**Focus for the next take is written by code, ranked by repetition, then severity, then size.** At most three items, each naming its mark and citing its number. Marks that diverged in two or more takes of the same script come first (most takes first), then full divergences before "close" ones, then the largest gap relative to the target: for `[KEY]`, the larger of the rate gap and the pause gap; for pauses, (target − measured) / target; for sections, |overrun| / budget. A `[DEFINE]` has no continuous measure, so it gets a fixed middle weight. "Diverged" means the same set of statuses as the take comparison (now one shared table in `compare.py`). If every mark was met the card says so and lists nothing; if nothing measurable diverged but some marks could not be measured, it says that instead. Alternatives: let the model choose (needs a key, which this must not), or rank by mark order (buries the biggest problem). History is real takes of the same script recorded before this one; examples and drills are never counted.

**Every status chip carries a glyph and words, not colour alone.** met ✓, close ~, diverged ✗, not measured –, as real text hidden from screen readers plus a visually hidden status word, in the report, the Improvise report, the take comparison and the legends. CSS `::before` was rejected because the status classes are also used on bars and words (it would leak), and generated glyphs are read inconsistently by screen readers.

**Chips that carry numbers are buttons; a click plays the moment and pins its tooltip.** The tooltip shows on hover, on keyboard focus, and stays pinned after a click until Esc or a click elsewhere (one at a time). Combining the two was the decision the brief asked for: a click already meant "hear this moment", and the numbers are what you want to read while hearing it, so one click does both rather than adding a mode. The tooltip text is also each chip's accessible description. Status lines are `role="status"` and are only written when their text changes (the Improvise countdown used to rewrite one every 200 ms).

**Analysis progress uses a background job and polling, not WebSockets.** One worker thread runs analyses in order (speech-to-text is serialized anyway), so a second take honestly shows "waiting" instead of pretending to run. The job id is the take id and the stage is saved in `take.json`, so a reloaded page or a restarted server can still answer "what happened to this take". The page polls every half second and shows decoding → transcribing → aligning → definition check (Improvise: decoding → transcribing → measuring). The synchronous endpoints are unchanged, so scripts and tests keep using them. Alternatives: WebSockets or server-sent events (more moving parts for a local app with one user).

## Practice loop (M11)

**A drill is judged against the median of the full take it came from.** One line has no median of its own (and a section's median would rest on a handful of lines), so a `[KEY]` line's "slower than your median" would be meaningless. The parent take's median is copied into the drill's `take.json` when the drill is created, so re-analyzing or deleting the parent later never changes what the drill was measured against. If the parent has no median, the rate is not compared and the drill says why; pauses are still measured. Alternatives: the median of all recent takes (mixes days and scripts), or the drill's own words (too few to mean anything).

**The pause after the drilled line is measured up to the end of the recording,** because there is no next line to stop at. The drill's sentence says so ("measured to the end of the recording"). It can over-count if the speaker waits before pressing Stop; that is the trade-off for measuring at all.

**Drills come only from your own full script takes, and stay out of everything else.** A drill is stored as a take with `kind: "drill"`, `drill_of` and the line or section range. It never joins take comparisons, focus history, the "latest median" used by Suggest marks, or the startup fallback, and the Takes list shows it under its parent. The example take (a synthetic voice) cannot be drilled: its median is not yours. A drill's sub-script is the line under its section's name without the budget (one line is not a section's worth of time), or the whole section with its budget; re-analyzing a drill keeps that sub-script.

**A/B playback uses the one shared audio element.** Each cell of the take comparison has a ▶ that plays that take from a little before the mark to just after it (the line for a `[KEY]`, the measured window for a pause). Starting another cell switches the same element's source, so two takes can never play at once; a timer, not `timeupdate` (every ~250 ms), stops it at the end of short pause windows.

## Alignment that survives real speakers (M12)

**Misheard words match by character similarity, only inside the gaps between exact matches.** After the exact `SequenceMatcher` pass, each stretch where the script and the transcript disagree is aligned again with a small order-preserving search that pairs words whose similarity (difflib ratio) reaches `fuzzy_match_ratio` (default 0.8, in Settings; 1.0 turns it off). Because it only runs between exact matches, a loose match can never cross one. Guards keep it from changing meaning: words shorter than `fuzzy_min_chars` (4), number words ("seventy" / "seventeen"), and a word that is the other with a negation prefix ("possible" / "impossible", "consistent" / "inconsistent") never match loosely. "their" / "there" can (a harmless homophone). A matched misheard word keeps what was heard, shown in the "what you said" view. On the example take this changed only the misheard line's coverage (0.875 → 1.0); every line's start, end and rate stayed the same. Alternatives: a full weighted alignment (Needleman–Wunsch) over everything, more code for little gain, or phonetic keys (Soundex), which would match "then" and "than".

**Spoken years are rewritten into the words digits become, on both sides.** Digits already normalize to cardinal words ("2019" → two thousand nineteen), so a cross-word pass rewrites "twenty nineteen", "nineteen oh five", "nineteen hundred", "fifteen hundred" and "two thousand and nineteen" into the same cardinal words, keeping each new token tied to the words it came from (so a year spoken as two words still gets both words' timestamps). It runs only on a maximal run of number words and line by line in the script, so "twenty five percent" and "1,200" are untouched. It lives in the aligner, not in `normalize_word`, which other checks use. Known limitation, tested: "fifteen twenty minutes" reads as the year 1520, so "15 to 20 minutes" said that way only partly matches. The tokenizer also now strips punctuation before reading a number, so "2019." at the end of a sentence is a number too.

**A `paraphrased` status times a reworded line without pretending to measure its pace.** A line below the coverage threshold is paraphrased when both neighbouring lines were found, the speech between them holds at least 2 words and `paraphrase_min_words_pct` (30 %) of the line's length (fillers not counted), and at least one of the line's own content words (at least `fuzzy_min_chars` letters, not a common word such as "this" or "which") is among those words. The last condition keeps an unrelated aside in place of a skipped line "not found", and it is a plain word overlap rather than "a word the aligner paired", because which short words the aligner happens to pair is arbitrary. The span then stops at a pause before the first and after the last of those words, so a neighbour's stray last word (and the pause after it) stays with the neighbour; review found that without this a 1.6 s pause after a `[KEY]` line was reported as missing. Numbers are also never joined into a year across a full stop ("…was 20. 15 of them…"). The line gets its start, end and duration from those words and counts toward its section's time; it never gets a words-per-minute rate (its words do not correspond to the script's), never enters the median, and a `[KEY]` on it is "not measured" on rate, "diverged" only if the pause after it is missing (never "close", which would imply a rate was checked). A pause mark at the end of the line is measured from its last word to the next line; marks inside it cannot be placed and say so. Two reworded lines in a row stay "not found": their words cannot be split between them honestly. Alternatives: lower the coverage threshold (would score reworded lines as if they were read), or treat the first and last line as bracketed by the start and end of the take (an opening ad-lib would then be timed as the first line).

## Defense Q&A practice (M13)

**Questions are proposed by the model from the script text only, and checked by code.** The model receives the script's lines with their indexes (never audio, never a take) and proposes five to eight questions, each tagged clarification, methods challenge, limitation or implication and tied to the line it is about. Code drops a question with an unknown tag, a line index outside the script, empty text, more than 200 characters (the Improvise topic limit, since the question becomes the topic) or a repeat, keeps at most eight, and tells the speaker how many it dropped and why. Without a key the button is disabled with a one-line reason; there is deliberately no template-based stand-in, because canned questions would look like the model's. Typing your own question needs no key.

**An answer is an ordinary Improvise take whose topic is the question.** All Improvise measures apply unchanged (time goal, pace, fillers, hedges, endings), and the take records the question, its tag and the script line in `improv.json`, so the report can say what was asked and "Answer it again" returns to the same question. Alternative: a separate Q&A mode, which would duplicate Improvise for no measured difference.

**"Answered the question" is one more content-review criterion, and it always needs a quote.** It is only asked when the take answers a question, and only in the opt-in content review. The other criteria may be "missing" without a quote (an absent hook has nothing to quote); this one may not, because "you did not answer" is the judgement most likely to be wrong and most in need of the speaker's own words behind it. Code finds the quote in the transcript and attaches its time, or drops the item, exactly as for the other criteria.

**The fake model proposes questions too, including two invalid ones,** so the validation is visible when the UI is tried without a key, and it fills in "Answered the question" so the review can be exercised. It stays labelled as a development stand-in.

## Import, portable settings, export and evidence tooling (M14)

**PowerPoint speaker notes are read with the standard library, not python-pptx.** python-pptx needs lxml and Pillow, both compiled, which goes against "a small pure-Python backend dependency" for what is a read of three kinds of XML part. `pptx_import.py` opens the file with `zipfile`, takes the slide order from `presentation.xml` and its relationships, the title from the `title` / `ctrTitle` placeholder and the notes from the notes slide's body placeholder. It refuses a file over 50 MB, any part over 5 MB, more than 2000 members or 200 MB of XML in total (a zip bomb), and names a password-protected or old `.ppt` file instead of failing on it. Each slide becomes `## Slide N: title` with no budget (the speaker sets those), a slide without notes gets `<!-- no notes -->`, and a hidden slide keeps its place with `<!-- hidden slide -->`. Notes are prose, so anything the mark parser would misread is changed as little as possible, keeping every word: a leading `##` is dropped, a standalone ` / ` loses its spaces, `<!--` cannot open a comment, a title ending in `[m:ss]` gets round brackets. `[KEY]`, `[DEFINE: term]` and `*word*` pass through, for speakers who already write marks in their notes. A section with no lines (a slide without notes) now reports "no script lines" instead of "not found": there is nothing to time, and "not found" would claim the speaker skipped it; it stays out of the whole-talk check, the focus list's "could not be measured" note and the outcomes file. Nothing is stored on the server: the text goes to the editor, which asks before replacing a script. python-pptx is a dev dependency, used only to build real decks in the tests.

**Settings can travel in the script, on its first line.** `<!-- take-two: short_pause_s=0.9 key_slower_pct=15 -->` as the first non-blank line sets those thresholds for takes of that script, over the Settings dialog (script, then dialog, then defaults). `marked:` is accepted too, the app's earlier name. Only the first line counts, so a settings-looking comment further down stays an ordinary comment, and nothing may follow its `-->` (the script starts on the next line). Names must be Settings field names; each value is checked against that field's own type and bounds, and how values combine (a pace band's minimum above its maximum) is checked together with the dialog's settings, because a minimum of 200 is fine with a maximum of 250. Anything wrong gives a 400 that names the setting (and suggests the nearest name for a typo) before a take folder exists, in every route that takes a script (new take, retry, re-analysis, drill). The editor shows the same message as you type, the Settings dialog badges the fields the current script sets, and the Rehearse tab disables recording with the message, because a take the server will refuse would otherwise be a whole talk recorded for nothing. A re-analysis that fails after Settings are saved now says why on the page. The values apply from speech-to-text on, because `conventions_enabled` changes the Whisper prompt. Every analysis stores the `settings` it used, the `settings_request` from the dialog and `settings_from_script`, and the report says which values came from the script. The evaluation harness applies the line too, over a recording's `settings.json`, and names it in `RESULTS.md`. A drill keeps the line, so it is measured with the same thresholds. Comments are blanked before the script is hashed, so editing the line keeps a script's history together; takes measured with different thresholds then sit in one comparison, as they already do when Settings change. Alternatives: YAML front matter (a new syntax and a parser to ship) or a settings file beside the script (lost when the script is pasted or shared).

**An exported report is one HTML file with the recording inside.** Inline CSS, the 16 kHz WAV as a base64 data URI, every tooltip's text printed under its line (there is no hover on paper or in an email preview), the same glyphs as the app, and a few lines of inline script so clicking a line plays it. It carries what the report shows: summary, focus, sections and the whole-talk cut, the conventions card when that preset is on, every mark with its numbers (pauses with Whisper's own gap, emphasis when on, coverage below 100 %), model suggestions labelled with the model that wrote them, and the transcript. An example take says it is a synthetic voice from its kind, not its name, so renaming it cannot hide that (the report shows a badge too). It loads nothing from the network, so it opens offline and an advisor needs nothing installed. Base64 makes the audio a third larger: about 43 KB per second of talk, so a 10-minute take is about 26 MB, and the app asks before downloading anything over 20 MB, using an exact size from the server. It stays in the light palette, which is what prints. Improvise reports are not exported (409): their page is built around measures without a script, and nobody asked for it. Alternatives: a PDF (a rendering dependency, and no audio), or a zip of HTML and WAV (two files to keep together, and an unzip before reading).

**Takes can be renamed, deleted, downloaded and summarized.** A new name is written to `take.json`, which every re-analysis reads, and to the stored analysis, under the take's lock, so it survives re-analysis. Any finished take can now be deleted, with its drills; a take or drill being analyzed is refused (409). The confirmation names the take, its date, its folder on disk, its size, how many drills go with it, and that it cannot be undone. Windows cannot delete a file that is open, and the shared audio element streams the take's WAV, so the client unloads the player first; the server retries for a few seconds and otherwise answers 409 with "still open". "Download folder" zips the take's folder exactly as stored, with its drills under `drills/`. `GET /api/outcomes.csv` lists every mark's status and numbers across all takes for a user study or a spreadsheet, with no labels, topics, script text, transcript or audio. Mark ids are therefore positions: `KEY:L6` and `/:L3:W4` as in `eval/`, but `section:S2` and `DEFINE:L4` instead of names, because section names and terms are script text. A drill's rows use the positions of its marks in the full take's script, so they line up with the parent's rows under `drill_of`; a line drill has no section row (it times a line, not the section). Drills can be renamed, exported, downloaded and deleted on their own. The script is identified only by its `script_key` hash. A `[KEY]` mark has three rows (overall, rate, pause after); example takes, unfinished takes and Improvise takes (no marks) are left out.

**The harness runs the real pipeline in a scratch takes folder.** Each recording goes through `pipeline.run_take`. With `--reuse-transcripts` it goes through `process_take` on a take whose transcript is already in place, as the example take does. `config.TAKES_DIR` points at a temporary folder that is removed afterwards. Alternatives: call `analyze` directly, which would skip decoding, the voice-activity detector and the `[DEFINE]` check, so it would not evaluate what the user gets; or use the real takes folder, which would mix evaluation runs into the user's history, comparisons and focus. Speech-to-text stays local: with cloud transcription configured, the harness refuses to start rather than send recordings away.

**A pause is matched to the human label that overlaps the app's stored window, and no overlap means the human heard 0 s.** The window is the one the report shows: from the end of the word before the mark to the start of the word after it. Matching on the analysis's own numbers keeps every compared value traceable to the JSON. Counting a missing human pause as 0 s, rather than dropping the mark, keeps a pause the app invented in the error. When Whisper smears a word boundary across the silence, the window can miss the labelled pause and the error counts against the app. That errs pessimistic, which is the right direction for evidence.

**Mark ids number lines from 1 and place pauses by the words before them.** `/:L3:W4` is the `/` after word 4 of line 3, so a labeller can read it off the script. The ids parse to the same keys the take comparison uses (`compare._key_marks`), so the harness cannot drift from the app's own idea of which mark is which. `--list-marks` prints them for a script.

**Aggregates are micro-averaged.** Every mark and line counts once, so a long talk weighs more than a short one. A per-recording (macro) average would let a 30-second clip with two pauses weigh as much as a 15-minute talk.

**The synthetic recording's "human" labels are the generator's ground truth, and are labelled as such.** `eval/make_synthetic.py` turns `fixture_truth.json` into the same files a person would make, so the harness runs end to end today. `RESULTS.md` says at the top that the only recording is a synthetic voice and that its numbers say nothing about real speakers. The note is driven by each recording's `info.json`, so it changes when real recordings arrive.

**Retest reports spread, not significance.** `eval/retest.py` gives n, min, max, range and the population standard deviation of the median wpm and of each pause across takes of one script. With three to five takes, a significance test would be theatre. No retest numbers go into the docs until real repeated takes exist.

**The recording path is tested in a real browser with Python Playwright, a dev dependency.** Unit tests cannot reach `getUserMedia` → `MediaRecorder` → upload → background job → report. `tests/test_browser.py` starts the server on a free port with a temporary takes folder and real local speech-to-text, then drives the installed Google Chrome (`channel="chrome"`) with its fake microphone playing the synthetic fixture (`--use-fake-device-for-media-stream`, `--use-file-for-fake-audio-capture`). It records about 35 s in script mode and about 15 s in Improvise, and fails on any uncaught page error. It is opt-in (`-m browser`, excluded by default) because it needs Chrome and loads the speech model, and it refuses to run against a stale `frontend/dist`. Python Playwright rather than the Node package because the tests already run under pytest, and it adds no frontend dependency; it is a pure-Python wheel plus its driver, and using the installed Chrome avoids downloading a browser.

**Smaller changes.** The deprecated FastAPI startup hook is now a lifespan handler that loads the speech model in the background. Dark mode follows the system setting: every hard-coded tint became a colour variable, and the dark palette lightens the status colours so they keep their contrast. Review in the browser found that the script editor's highlight layer had picked up the global `code` style (monospace, 13 px, grey) while the textarea underneath is 17 px serif, so the caret and selection drifted away from the visible text; the layer now inherits the textarea's font, and marks are shown with colour only (no bold, no smaller monospace) so every glyph keeps its width. A one-minute tour on the Script tab marks the first `[KEY]` line and the first line with a ` / ` in the editor itself (comments and headers skipped, since the sample's help comment shows a ` / ` too), explains each in the side column, offers the sample script when there is no such line, and is remembered once dismissed (browser storage; "Show the one-minute tour" brings it back). Coaching suggestions now record which model wrote them, so an exported report can say so.

## Any speaker (M15)

**Take Two is positioned for anyone who has to land an idea out loud, with science talks as one example among several.** The README, write-up and pitch now lead with the problem every scripted speaker shares (one universal standard cannot tell a deliberate pause from a lost place) and name four audiences in order: technical and academic talks, celebratory speeches, performance poetry and slam, pitches and interviews, each with a sentence on what landing it means there. No usage, quotes or comparisons were added that the repository cannot back. The model prompts for suggested marks, `[DEFINE]` checks and Q&A questions no longer assume a science talk or a scientist; their behaviour, caps and validation are unchanged, and the Q&A tags stay the same four (a "methods challenge" reads as "how do you know" for a pitch too). The `[DEFINE]` prompt version hash changes with its wording, so cached judgements are asked again once.

**No new mechanics, because the marks already describe intent rather than a style.** `[KEY]` is "this line must land", which is the result in a talk, the sincere line in a toast and the last line of a poem; it is still measured against the speaker's own median. `/` and `//` are deliberate silences, which is the room's laugh in a toast and the breath at a line break in a poem; the thresholds were always the speaker's. `[DEFINE: term]` is "my audience may not know this", which covers a family in-joke a toast must set up or a reference in a poem as well as a technical term; the check (explained aloud at or before first use) does not care what kind of term it is. Alternatives: per-genre modes or genre-specific marks (more syntax to learn, and they would smuggle a genre's norms back in as defaults).

**Two short scripts were written for the demo, and say so.** A wedding toast (one `[KEY]`, `/` for the room's reaction, `//` before the last line, one `[DEFINE]` for a family phrase) and a slam poem (line breaks as `/`, a `//` before the turn, three emphasised words), each under 90 seconds, sit in `examples/scripts/` and are offered with the science sample and the demo speech under **Start from an example** on the Script tab. Names are made up. The demo speech keeps its structure and planted mistakes, but its examples now include a toast and a poem, so it no longer reads as if talks were the only use. A "Toasts & occasions" Improvise category was added; the existing categories are unchanged.

**The write-up is built and checked by a script.** `scripts/writeup_pdf.py` turns `WRITEUP.md` into `WRITEUP.pdf` with the installed Chrome through Playwright (already a dev dependency), checks that it prints on one US Letter page and that a heading names each section the submission requires, and has a `--watch` mode for editing. Alternatives: ReportLab (what produced the earlier PDF, by hand; a new dependency and a second layout to keep in step) or a Markdown library (also a dependency, for a page that uses five constructs).

## Hear it: the voice demonstrates a line (M16)

**The cue plan is derived from the marks by the same rules the analysis uses, in pure backend code.** `delivery.marked_plan` reads a parsed line and Settings and returns segments (text, pace as a multiple of the reference and in wpm, pitch shift, contour, loudness, stress, pronunciation, pause after, `source`, `checked`). `/` and `//` are the speaker's own `short_pause_s` and `long_pause_s`; `[KEY]` is `key_slower_pct` below the median and then `key_pause_after_s`. The demonstration and the report therefore cannot disagree about what a mark asks for. The reference pace is the median of the take the line came from (a report or drill), else the speaker's latest take (as Suggest marks already does), else `hear_baseline_wpm` (150), which the plan and the UI call "a typical baseline, not your own rate". A line with no marks is one plain segment with a note. Alternative: let the frontend derive the plan (two parsers to keep in step, and no unit tests without a browser).

**"Checked" means the report measures that cue; everything else says "demonstration only".** Pauses and `[KEY]` are always checked. `*word*` is checked only when the emphasis check is on in Settings, and says so when it is off. A `[SAY]` pronunciation is never checked: nothing in the report measures pronunciation. Coach cues are never "checked" as they stand. Those with a mark equivalent (a pause, a stressed word) say they become checked once accepted into the script; a contour, a slowed word, a softer phrase, a build and a pace change say "demonstration only, not checked". Prosody could measure a rising end (Improvise does), but script reports do not, so it is not claimed.

**The coach's version adds to the speaker's marks and never removes or shortens one.** The model (or the heuristic) proposes cues as spans of the line's words. Code keeps a cue only if its words are a verbatim span of the line (ignoring case and edge punctuation), it has a reason (cut to 20 words), it is not a duplicate, stress covers at most two words and at most two stresses per sentence, and at most six cues survive. Numbers are clamped: pace −30 to +15 %, pause 0.2 to 2.5 s. A pause no longer than one the speaker wrote is dropped ("a pause you wrote is already at least as long"); a longer one lengthens the silence, which still meets the speaker's mark. The coach's overall pace never applies to a `[KEY]` line: the speaker's rate wins and the plan says so. Dropped cues are counted on screen, as Suggest marks does. Conflict noted: the brief asks for the coach to say "where a pause the user wrote should be longer or shorter", and also that written marks are never overridden. Shortening would override, so the coach may only lengthen.

**Registers are opt-in starting points, which keeps "no universal standard".** The four registers (conversational / technical, celebratory, slam, pitch) are data in `delivery.REGISTERS`, each a description of what landing it means and a few plain rules. They are off by default (`hear_register = "none"`). They shape only the coach's demonstration, never a measurement, a status or the report. The amounts are the speaker's own: `coach_slow_pct` (how much slower a slowed word is) and `coach_pause_s` (an added pause), both in Settings. Without an API key the coach's version is the picked register's heuristic (`heuristic_coach`), labelled "heuristic: the … register's rules, not a model" and tagged `register:<name>` in every segment it touches. With neither a key nor a register it is off with a one-line reason, rather than silently applying a generic style. With a key and no register, the model decides from the line alone, and its output is labelled with the model's name. The heuristics are deliberately plain: slow the first number in a sentence, stress the last content word of a sentence (new information tends to come last), a falling end on statements and a rising end on questions, a beat between sentences; in a toast, room after a sentence, the `[KEY]` line softer, the last line slowest with a long silence; in slam, a build across the line's phrases and a drop on its last, a held end except on the last line; in a pitch, slow numbers and stress the ask. Heuristic output goes through the same validation as the model's. Alternative: register rules as a universal default (exactly what the product argues against).

**The model reads the line, its neighbours, the speaker's marks, the register and the reference pace: text and numbers only.** One structured call per line, cached in memory by prompt and provider, so switching back and forth costs nothing. The prompt says this is one way to say the line, not the correct one, and the UI repeats it. The fake model (`TAKE_TWO_LLM=fake`) proposes one cue that is not in the line, so the drop is visible.

**Accept into script reuses the Suggest marks writer.** `delivery.accept_rows` turns accepted pause and stress suggestions into rows for `suggest.apply_marks`, which gained an `emphasis` row (`*word*`, punctuation kept outside) and now keeps `[SAY]` marks when it rebuilds a line. On the report, Accept is offered only when the Script tab's script has the same lines as the take, so a mark cannot land on the wrong line.

**The browser's own voice is the default.** `speechSynthesis` is local, needs no key and no network, and sends nothing. Each segment is one utterance with its rate, pitch and volume, and a pause is a timed gap after the utterance ends, never left to punctuation. A contour is approximated by saying the segment's last word as its own utterance, pitched up (rise) or down (fall); the panel says that browser voices give coarse control of pace and pitch and none of tone. A browser voice's own pace at rate 1 is unknown, so rates keep the plan's ratios against an assumed 170 wpm, and the panel shows the plan's wpm, not a claim about the voice. Some browsers load voices after the page: the panel waits for `voiceschanged`, and with no voice it shows the plan as text and says why. The voice picker marks a browser voice that is provided online (Chrome's "Google" voices send text to Google). The scheduling is a pure, import-free module (`frontend/src/schedule.ts`) tested under Node's built-in runner; the two built-in modules it needs are typed in a small shim, so the frontend gains no dependency, not even `@types/node`.

**The optional SSML voice is Azure Speech.** Azure supports what the plan needs in one request: `<break>`, `<prosody rate pitch volume>`, a pitch `contour` for real rising and falling ends, `<emphasis>`, and `<phoneme alphabet="ipa">`. It is reached with one HTTPS POST and a key, through httpx (already installed with the Anthropic SDK). Amazon Polly needs AWS request signing (boto3 or hand-written SigV4) and has no contour. Google Cloud TTS needs project setup and has no contour either. `tts.compile_ssml` is pure: text is XML-escaped, every number is bounded (rate ±50 %, pitch ±6 st, volume ±50 %), breaks are capped at 5 s and text at 2000 characters, and a `[SAY]` becomes `<phoneme>` with IPA or `<sub alias>` with the respelling. The provider is used only with `TAKE_TWO_TTS=azure` and both Azure variables. It is never chosen automatically: the speaker picks it in the voice picker, which first asks for consent naming exactly what is sent ("the text of the line you play (script text, no audio)"). The server refuses a request without that consent flag, and the privacy banner names it. Without a key it is disabled with a one-line reason, and nothing falls back to it silently. A `fake` provider renders the plan as tones and silences (labelled as tones) so the UI and the tests run offline. The real Azure endpoint has not been called from this machine. Synthetic audio plays through its own audio element, never the shared take player, and is never written to a take folder.

**Pronunciations are proposed by a model and owned by the speaker as `[SAY: word = RESPELLING | ipa]` marks.** A mark in the script (rather than a separate lexicon file) travels with the script like the settings line and needs no storage, and the parser already strips bracket tags before alignment. It is script-wide: Hear it uses it wherever the word appears, including the possessive ("Maya's" uses Maya's mark). Flagging needs no model. A run of capitalised words inside a sentence is a name (titles such as "Dr." do not end a sentence; a possessive marks a name even first in a sentence). All capitals is an acronym, letters beyond ASCII mark a loanword, and a lowercase word of seven or more letters is uncommon if the speech recognizer's own tokenizer splits it into three or more pieces. That last check is a word-frequency list the app already has: Whisper's tokenizer is on disk once the speech model is downloaded, and common words are single pieces in it. Without it the rule is skipped and the list says so. CMUdict was considered and not added: it would supply pronunciations without a key, but its coverage of names is poor, and a confident dictionary pronunciation of a name is the error this feature most needs to avoid. Without a key nothing is proposed; the speaker types the respelling. A model's proposals are kept only for flagged words with a plain respelling (letters, hyphens, apostrophes, at most 40 characters), at most 12, labelled "proposed pronunciation: confirm it". Confirming writes one `[SAY]` mark at the end of the word's first line and removes earlier ones for that word. "Hear one word" says the respelling's syllables slowly, the capitalised (stressed) one higher and louder, then the whole word at an ordinary pace.

**Words that may not have been clear come from the recognizer's measurements.** A script word on a line that was found is listed when its recognizer confidence (the lowest `Word.prob` of the transcript words it matched) is below `clarity_prob` (0.5), or when the alignment matched it to a different word it heard (M12's misheard words). The brief asks to skip words the recognizer was unsure of only because they sit inside a confidently matched span, with a threshold and a minimum count in Settings. That is read as: an exactly matched low-confidence word is skipped when the `clarity_context_words` (2) words on each side all matched exactly at 0.9 or more (0 turns the skip off). The wording is fixed and measured ("The recognizer was unsure of “water” (confidence 0.30)."; "The script says “bleaching”; the recognizer heard “leaching” (confidence 0.57)."). "You said X" was rejected: the app knows what the script says, not what was said. One line on the card says a recognizer can miss a word because of an accent, a noisy microphone, a rare word or a quiet moment. "I said it fine" stores the word in `clarity_dismissed.json` next to the takes and leaves it out of every later analysis; it can be undone. Takes analyzed before M16 show the card after a re-analysis. **Drill this word** is a new drill kind (`word`): the drill script is the word alone, with its `[SAY]` mark, and the drill's sentence is what the recognizer heard and its confidence. It joins no comparison, and the outcomes file gives it no section row.

**Not done: Hear it on the teleprompter, and the spoken debrief stretch.** The teleprompter is where the speaker records, and a voice there would have to be locked out while the microphone is open. The Script tab's list already covers every line before rehearsing. The spoken debrief (reading Focus for the next take aloud) was left for later rather than added half-finished.

## Spoken examiner (M17)

**Recording starts only after the examiner has finished speaking.** A microphone open during the question would record the synthetic voice into the answer, and the measurements (pace, hesitation, the words themselves) would be the examiner's. The session is a pure state machine (`frontend/src/examinerMachine.ts`): idle → asking → thinking → recording → analyzing → a follow-up round or the next question → done. "Recording" can be entered only from "thinking", and "thinking" only once `speak()` has resolved, so there is no path to an open microphone while the voice plays. Leaving "asking" stops the voice, the recorder is started only after every voice is stopped, and a short cue tone marks the start of the thinking time and ends before the microphone opens. The Chrome test traces every voice start and end and every microphone open and close and fails if they overlap. Alternative: echo cancellation with the microphone always open. That would hand the answer's audio to the browser's processing, which the recorder deliberately turns off for honest loudness and pitch, and it would still capture some of the voice.

**The end of an answer is found by a pure silence detector over the meter's level samples.** The first 0.4 s of each recording sets the room's level; speech is at least 12 dB above it for a quarter of a second. Nothing ends an answer before speech has started, however long the quiet (a thinking speaker is not done). After speech, a silence longer than `examiner_silence_s` (3 s) ends it, and `examiner_max_answer_s` always does. A click is not speech. No library: a dozen lines, tested with level series. Space ends an answer at once, for a noisy room where the silence never comes.

**One follow-up per question, and never a heuristic one.** A session must not run away, and a follow-up to a follow-up stops being a Q&A rehearsal and becomes a conversation the speaker did not plan time for. The state machine asks at most one per question and never one for a follow-up's answer. The server stores the follow-up in the answer's `improv.json`, so asking again returns the same one without a second model call, and refuses one for an answer that is itself a follow-up. The model reads only the question, the answer's transcript text and three measured numbers (spoken seconds, words per minute, seconds before the first word); never audio, never the script. Code keeps the first item that is one question (one question mark outside quotes, one sentence, at most 30 words), names the words of the answer it builds on, and finds them in the transcript. Any phrase it quotes must be in the transcript, or in the script the client sends only for this check. Everything else is dropped and counted. Without a key there are no follow-ups and the page says so: a template follow-up ("Can you say more about that?") would look like the examiner listening when nothing was read. `TAKE_TWO_LLM=fake` proposes one valid and one extra follow-up, labelled as the fake.

**Keyboard control rather than voice commands.** Space, R, S and Esc work at every moment and are shown on screen. Spoken commands would need a speech recognizer listening for them between answers. That means another recognizer (in-browser recognition sends audio to Google, which breaks "audio stays local") or the local model running continuously. And "skip" said inside an answer would end it. The speaker's hands are on their notes, but a key under a thumb is enough; nothing needs the mouse once the session starts.

**A session is a label and a `session` entry in each answer's `improv.json`, not a new storage format.** Each answer is an ordinary Improvise take whose topic is the question, with the Improvise measures, Takes listing, comparison, export and failed-take recovery it already has. `session` holds the session id, the question's index, the total and, for a follow-up's answer, the answer it follows up. It is validated on the way in (an id of letters, digits and hyphens; numbers in range; a real take id), and the label says "Examiner 10:42 · Q2" or "follow-up to Q2". `GET /api/improv/session/{id}` gathers the answers by reading the takes. A separate session file was rejected: it would duplicate what the takes already know, and a crash between writing the two could make them disagree. An interrupted session keeps every answer already sent. An answer whose analysis fails keeps its folder with Retry, as any take does, and the session moves on to the next question.

**The closing line is written by code from the numbers.** How many questions (and follow-ups) were answered; how many answers stayed within, were close to, or were outside the speaker's own Improvise pace band (the same statuses the Improvise report uses); the longest wait before an answer's first word, measured from when recording started after the thinking time; how many questions were skipped. No model, no score, no grade, and the same text is on screen with a link to each answer's report. The examiner reads it aloud only when at least one answer was recorded.

**No voice or no microphone: say which, and offer the typed path.** Before the session starts, the page waits briefly for the browser's voices. Without any, it says the examiner cannot ask aloud and links to "Questions about my script", where the same questions can be read and answered or uploaded. If the microphone is refused when the first answer begins, the session stops, says so with the browser's own message, and links to the same place. The examiner's voice has its own picker (and can be the configured server voice, behind the same consent as Hear it).

**A bound found by the test.** The first browser run seeded an answer length of 8 s, below the setting's minimum of 10 s. The server refused every answer as invalid settings (as it should), and the session carried on with each answer showing Retry. That is the failure path working, but it also shows that settings are only clamped in the dialogs. Values set outside them (an older build, a hand-edited browser store) are refused per take rather than corrected. Not changed here; noted in TESTING.
